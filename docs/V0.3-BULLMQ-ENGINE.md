# ATSI AI Hub — Moteur d'exécution BullMQ V0.3

## Objectif

Renforcer la fiabilité du moteur d'exécution des agents,
en conservant PostgreSQL comme source de persistance
et Redis/BullMQ comme système de traitement des tâches.

Les mécanismes de diagnostic ne doivent pas modifier
automatiquement les exécutions existantes.

## Architecture

Composants concernés :

- NestJS : création et suivi des exécutions
- PostgreSQL : persistance des états d'exécution
- Redis / BullMQ : gestion de la file de tâches
- Worker TypeScript : traitement des jobs
- Modules de diagnostic : analyse des incohérences

File BullMQ existante : atsi-agent-tasks.

## États d'exécution PostgreSQL

Les états reconnus sont :

- queued : exécution en attente
- running : exécution en cours
- completed : exécution terminée avec succès
- failed : exécution terminée en échec

Les transitions sont contrôlées afin d'éviter
les changements d'état non autorisés.

## Sécurité du worker

Les options de sécurité du worker comprennent :

- une concurrence limitée à une exécution
- une politique explicite de gestion des jobs bloqués
- des transitions PostgreSQL contrôlées
- l'absence de reprise automatique des exécutions

La configuration actuellement développée utilise
maxStalledCount = 0.

Cette configuration ne garantit pas à elle seule
l'absence de toute nouvelle livraison d'un job.

## Diagnostic PostgreSQL / BullMQ

Le diagnostic compare :

1. L'état PostgreSQL d'une exécution
2. L'identifiant BullMQ associé
3. L'état réel du job BullMQ

Le diagnostic est conçu en lecture seule.

### Résultats possibles

- consistent : états compatibles
- manual-review-required : divergence détectée
- indeterminate : informations manquantes ou inconnues

Une divergence n'entraîne aucune correction automatique.

### Correspondances compatibles

| PostgreSQL | BullMQ |
| --- | --- |
| queued | waiting |
| queued | delayed |
| queued | prioritized |
| running | active |
| completed | completed |
| failed | failed |

Les autres combinaisons connues nécessitent
une analyse manuelle.

Un job absent, un état inconnu ou une exécution
PostgreSQL manquante produit un diagnostic indéterminé.

## Tests

Validation de la suite worker :

- 74 tests exécutés
- 74 tests réussis
- 0 échec
- 0 test ignoré

Les tests de l'adaptateur utilisent des dépendances
simulées et ne nécessitent pas de connexion aux
services PostgreSQL ou Redis de production.

## Limites actuelles

- Le diagnostic est développé et testé en isolation.
- Son intégration au flux opérationnel reste à décider.
- Aucune réparation automatique des divergences.
- Aucune relance automatique d'une exécution interrompue.
- Les tests isolés ne remplacent pas une validation
  d'intégration sur des services réels.
- La journalisation détaillée et le suivi des étapes
  relèvent de l'étape 6 de la roadmap V0.3.

## Principes de déploiement

Avant toute intégration aux services actifs :

1. Vérifier les modifications de configuration.
2. Exécuter les tests appropriés.
3. Vérifier la compatibilité avec les données existantes.
4. Préparer une procédure de retour arrière.
5. Ne pas redémarrer les services de production
   sans validation explicite.

## Conclusion

Le socle de diagnostic du moteur BullMQ V0.3
permet d'identifier les divergences entre PostgreSQL
et BullMQ sans modifier automatiquement les données.

Les mécanismes de journalisation et de supervision
seront abordés dans les étapes suivantes.
